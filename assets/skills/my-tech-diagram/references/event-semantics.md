# 领域事件语义核验（画图前，本轮只读一次）

## 判定，先于命名和配色

| 类别 | 判断标准 | 示例与处置 |
|---|---|---|
| 业务命令 | 行为意图，可拒绝/失败；不是已经发生 | 创建订单、取消订单；放命令列 |
| 领域事件 | 已发生、有业务意义、可由领域专家解释的事实；有来源与责任归属 | 订单已创建、合同已签署；放事件列 |
| 查询 | 读取信息，没有业务状态改变 | 查询订单；单贴，不补“订单已查询” |
| 状态 | 当前快照/枚举值，不含发生了什么 | 待支付不是事件；“订单已进入待支付状态”也不能仅换词就算业务事件，须有真实转变与业务意义 |
| 技术动作/信号 | 处理或基础设施运行结果 | 缓存已失效、消息已重试、索引已同步，默认放技术机制图/日志设计，不混入领域事件 |
| 集成消息 | 传输业务事实或技术信号的契约 | topic不等于领域事件；一个领域事件可以不发MQ，也可以形成多个集成消息 |

某个技术结果确有明确业务含义时依据当前业务语境判断，例如“报价已发布”可是真实业务事实，不能仅因涉及索引或缓存而排除。技术失败也不自动等于业务失败：支付请求超时不证明支付失败，需待查询/回调确认。区分提出的新设计与代码已实现/真实发生的事实。

## 一份可追溯清单

每项记录：稳定ID、业务名称、来源（需求/代码位置/用户确认，或“提议”）、所属领域/上下文、触发类型及名称、前置条件、已确认业务结果、后续反应（若已确认）。

- 一条命令可以无事件、一个或多个事件；相同技术重试不能重复建模成多种业务事件。
- 合法事件可以由定时触发、外部事实或策略引起，不必补造用户命令来凑配对。事件单贴时在小字注明真实触发来源；事件间的顺序放总体时序图表达。
- 事件归属按谁拥有业务事实/规则和一致性边界决定；消费者不成为同一事件的另一个发布者。多个上下文同名概念需限定名称。
- 不只按名词聚类自动宣布上下文边界；结合业务语言、规则归属、现有代码/团队集成责任验证。核心/支撑/通用分类没有依据就标待定，不按电商例子套用。
- 图中每张事件贴必须能回到这份清单；不照抄参考图中的合同/权限等业务内容。

## 交付校验

先检查“是否为有来源的业务事实”，再检查过去式命名（如订单已创建）。后缀带“已”并不证明它是事件。不把建模清单说成已经实施的Event Storming工作坊。

最终交付仍是用户约定的**一张分组便签图**：黄命令、绿事件、粉分组；无关系线/箭头/时间轴。它用于汇报模型盘点；**总体时序图**另行表达命令交互、因果与顺序，关键机制图解释事务/缓存/幂等失败恢复。各图复用同一套事实、名称和ID，不反复建模。
