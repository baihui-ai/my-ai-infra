# PM 及其他常用图行业画法参考

> 供按需加载。覆盖：甘特图、里程碑/Roadmap、ER 图、DFD/流程图、BPMN（一句话）、网络拓扑图。
> 术语保留英文。UML 系列（Sequence/Class/Activity 等）见 `uml-diagrams.md`。

---

## 1. Gantt Chart（甘特图）

### 用途与适用场景
按时间轴展示任务排期与并行关系。判断标准：**要回答「什么时候做什么、谁和谁并行、延期会影响谁」时用它**。典型场景：项目排期、发布计划、跨团队依赖协调。不适合表达逻辑分支（用流程图）或交互顺序（用时序图）。

### 元素与视觉约定

| 元素 | 画法 | 说明 |
|---|---|---|
| Task bar（任务条） | 横向圆角矩形，长度 = 工期 | 条内/条旁写任务名；完成度用深色填充百分比 |
| Milestone（里程碑） | **菱形 ◆** | 零工期事件（如「上线」「评审通过」），只标日期点 |
| Dependency（依赖箭头） | 从前置任务条右端 → 后继任务条左端的折线箭头 | 默认 Finish-to-Start（FS）；其他类型需标注 SS/FF/SF |
| Critical path（关键路径） | 任务条与依赖箭头用强调色（常用红/橙）高亮 | 总浮动为 0 的任务链；任何延误直接拖垮总工期 |
| Swimlane / 分组 | 左侧分组标题 + 背景色带隔行 | 按团队/模块/阶段分组；组内任务纵向排列 |
| Today 线 | 垂直虚线贯穿全图 | 标当前日期，区分已完成/进行中/未开始 |

### 布局规则
- 时间轴在顶部（或底部），左→右流逝；刻度粒度按项目周期选（周计划用天、季度计划用周）。
- 任务纵向排列顺序 = 执行先后顺序（自上而下）；同组内也尽量按开始时间排。
- 依赖箭头只画「必要的」，全连接会变成意大利面条；汇总公司级里程碑单独放顶部一行。
- 一张图控制在 ~30 个任务条以内，超出按阶段/团队拆图。

### 门禁：最小信息清单

必需项（缺一项就不画）：
- [ ] 每个任务：任务名 + 起止日期（或开始日期 + 工期）
- [ ] 任务间依赖关系（谁阻塞谁；若确实无依赖，用户需明确表示「无依赖」）
- [ ] 里程碑节点及其日期（若用户明确表示没有里程碑，可豁免）

推荐项（缺了不拦截，但要在图上或回复中说明未提供）：
- 关键路径高亮（有依赖链时可由 CPM 机械推导，属计算非编造；数据不足时不标并说明）
- 分组/负责人归属（泳道或标签）——提供时增强可读性，未提供则按任务顺序平铺

### 常见错误
- 只有任务条没有依赖箭头 —— 退化成「彩色日历」，失去甘特图的核心价值
- 里程碑画成短任务条（应为零工期菱形）
- 关键路径凭感觉标红，没做 CPM 计算
- 时间轴刻度不均匀（工作日/周末混排导致条长失真）

## 2. Milestone Chart / Roadmap（里程碑图 / 路线图）

### 用途与适用场景
比甘特图更高层：**向管理层/外部讲「方向与节奏」，不讲任务细节**。判断标准：受众关心「几个关键节点、大概什么季度」而非具体排期时用 Roadmap；需要精确到天的依赖管理时回退到甘特图。

### 元素与视觉约定

| 变体 | 画法 | 适用 |
|---|---|---|
| Timeline 式 | 单条水平时间轴，里程碑菱形/圆点挂在轴上，上下交替标注 | 单一产品线、事件少（<15 个） |
| Swimlane 式 | 横轴 = 季度/月份，纵轴 = 团队/产品线/主题，条块表示工作流 | 多团队并行，最常用 |

- 时间粒度：**季度（Q1-Q4）或 Now/Next/Later 三档**，后者不承诺具体日期，适合不确定性高的规划。
- 条块内写主题名（3-6 字），不写任务分解；状态用颜色区分（planned / in-progress / done）。

### 布局规则
- Swimlane 式：泳道数 ≤ 6；每条泳道同一时间段内条块不超过 2 个，避免读起来像甘特图。
- 里程碑菱形放在泳道条块的端点或独立「里程碑」泳道。
- Now/Next/Later 式用三列卡片布局，不用时间轴。

### 门禁：最小信息清单
- [ ] 时间刻度（季度/月份 或 Now/Next/Later）
- [ ] 每个条目：主题名 + 所属时段
- [ ] 至少标注关键里程碑（发布日、评审点）
- [ ] 泳道归属（团队/产品线）

### 常见错误
- 把 Roadmap 画成粗粒度甘特图（塞入任务依赖箭头）—— 受众错位
- 时间承诺过细（在外部 Roadmap 上写死日期）
- 泳道超过 6 条，一屏读不完

## 3. ER Diagram（实体关系图）

### 用途与适用场景
描述数据模型：实体、属性、关系基数。典型场景：数据库设计评审、领域建模、新表结构沟通。判断标准：**要回答「有哪些表/实体、谁关联谁、一对多还是多对多」时用它**。

### 元素与视觉约定
**业界主流是 Crow's Foot（乌鸦脚）记号**（draw.io、dbdiagram.io、MySQL Workbench、Lucidchart 默认），Chen 记号仅教学场景。

| 元素 | Crow's Foot 画法 |
|---|---|
| Entity | 矩形，顶部实体名，下方逐行列属性 |
| Primary Key | 属性名**下划线**（或 `PK` 前缀标记），置属性区首行 |
| Foreign Key | 标 `FK`；也可加 `(FK1)` 编号区分多个外键 |
| 关系线 | 实体间连线，两端符号表达 cardinality + optionality |

Crow's Foot 端点符号（读法：「外侧符号 = 最大基数，内侧符号 = 是否可选」）：

| 符号 | 含义 |
|---|---|
| 单竖线 `|` | one |
| 三爪乌鸦脚 `<` | many |
| 圆圈 `O` | zero（可选） |
| `O<` | zero or many（最常见的外键端） |
| `||` | exactly one |
| `|<` | one or many |

Chen 记号（了解即可）：实体 = 矩形、属性 = 椭圆（主键下划线）、关系 = 菱形，基数在线旁写 `1`/`N`/`M`。

### 布局规则
- 核心实体居中，关联实体按引用方向向外辐射；避免连线交叉，交叉时调整布局而不是绕线。
- 多对多关系必须拆解为中间关联实体（junction table）再画。
- 属性列克制：讲设计时只列关键字段（PK/FK/核心字段），加 `...` 表示省略；完整 schema 给数据字典。
- 一张图 ≤ 15 个实体，超出按子域拆图（每图重复出现的实体用浅色标「外部引用」）。

### 门禁：最小信息清单
- [ ] 实体名（名词、单数）
- [ ] 每个实体的 Primary Key（下划线或 PK 标记）
- [ ] 每条关系的两端 cardinality（Crow's Foot 符号）
- [ ] Foreign Key 标注
- [ ] 多对多已拆中间表

### 常见错误
- 混用 Chen 与 Crow's Foot 两种记号
- 漏标可选性（`O`），只标 1/N —— 「一个订单可以没有优惠券吗」读不出来
- 关系线上没写关系名/动词短语（如 `places`、`contains`），只剩基数
- 把流程信息画进 ER 图（ER 图无方向语义，不表达「先做什么」）

## 4. DFD（Data Flow Diagram）与 Flowchart（流程图）

### 何时用哪个
- **DFD**：回答「数据从哪来、被谁加工、存到哪去」。系统分析、数据管道、安全边界（信任边界）分析用。可分层（Context → Level 0 → Level 1）。**无控制流语义**：不表达先后顺序、没有判断分支。
- **Flowchart**：回答「下一步做什么」。算法逻辑、审批流、故障排查步骤用。有严格顺序与分支（菱形判断）。
- 经验法则：动词是「流（flow）的是数据」用 DFD；「流的是控制」用 Flowchart。

### DFD 元素与视觉约定（Yourdon-DeMarco / Gane-Sarson 两系等价）

| 元素 | Yourdon-DeMarco | Gane-Sarson | 说明 |
|---|---|---|---|
| Process（加工） | 圆形 | 圆角矩形（带编号区） | 动宾短语命名（`校验订单`），编号 1.0/1.1 支持分层 |
| Data Store（数据存储） | 两条平行线 | 开口矩形（左侧 ID 格） | 名词命名（`订单库`） |
| External Entity（外部实体） | 矩形 | 矩形（可加阴影） | 系统边界外的数据源/归宿 |
| Data Flow（数据流） | 带标签箭头 | 同 | 标签 = 数据名（名词），不是动作 |

硬性规则：数据不能直接在 Entity↔Entity、Entity↔Store、Store↔Store 之间流动，必须经过 Process；Process 必须有进有出（不能只有输入或只有输出）。

### Flowchart 元素与视觉约定

| 元素 | 画法 |
|---|---|
| 开始/结束 | 圆角矩形（Terminator） |
| 处理步骤 | 矩形 |
| 判断 | 菱形，出支标 Yes/No |
| 输入/输出 | 平行四边形 |
| 流向 | 自上而下为主，回流线走侧面 |

### Flowchart 布局规则

- **连线不相交（硬规则）**：主流一条主轴；回流/驳回线统一走画布外侧（左缘或下缘）通道绕行，不与主流交叉；多条回流汇入同一节点时，各自在不同高度水平汇入、最后一段共用。宁可放大画布、移动节点，也不要让线穿线。
- 判断菱形的分支左右/上下对称出支，Yes/No 标签贴近分支根部。
- 同层节点顶部对齐、等距平铺。

### 门禁：最小信息清单
- DFD：
  - [ ] 每个 Process 有编号 + 动宾名 + 至少一进一出
  - [ ] 每条 Data Flow 有数据名标签
  - [ ] External Entity 与 Data Store 区分清楚
  - [ ] 分层编号一致（父图 Process 3 展开为子图 3.1/3.2）
- Flowchart：
  - [ ] 唯一开始节点，每个路径可达结束
  - [ ] 每个判断菱形的所有出支都有条件标签
  - [ ] 无悬空箭头、无未连接节点

### 常见错误
- DFD 里画判断菱形/控制流 —— 概念混用，是最常见错误
- Data Flow 标签写成动词（应是名词：流动的「东西」）
- Flowchart 判断分支漏标 Yes/No
- 一张 DFD 超过 7±2 个 Process 还不分层

## 5. BPMN 及其他行为图（一句话）

- **BPMN 2.0**：当流程涉及跨角色/跨系统的业务协作、需要表达事件（定时/消息/异常）、网关语义（并行/排他/包容）或要交给 BPM 引擎执行时，用 BPMN 代替普通流程图；否则用 Flowchart 即可，不要为简单流程引入 BPMN 的符号开销。
- **State Diagram（状态图）**：见 `uml-diagrams.md`，对象生命周期状态迁移用它。

## 6. Network Topology Diagram（网络拓扑图）

### 用途与适用场景
展示网络设备与链路：分区（VPC/子网/DMZ）、边界（防火墙/网关）、流量路径。场景：上云方案、安全评审、故障定位。

### 元素与视觉约定
- 用厂商/标准图标：路由器、交换机、防火墙（砖墙）、负载均衡器、云（Internet 用云形）。
- **分层分区框**：虚线圆角矩形表示安全域（`DMZ`、`内网`、`VPC 10.0.0.0/16`），框左上角标域名。
- 链路：实线 = 物理/主链路，虚线 = 备用/管理通道；标注带宽、协议或端口（如 `HTTPS:443`）。
- 流量方向用箭头，非双向时务必单向。

### 布局规则
- 自上而下：Internet/云 → 边界（防火墙/LB）→ DMZ → 应用层 → 数据层。
- 同层设备水平对齐；链路尽量避免交叉。

### 门禁：最小信息清单
- [ ] 每个节点：设备/服务名 + IP 段或 hostname（按需脱敏）
- [ ] 安全域边界（分区框）明确
- [ ] 关键链路标注协议/端口
- [ ] 出入方向箭头正确

### 常见错误
- 只有设备没有分区边界 —— 看不出信任边界在哪
- 链路不标协议端口，安全评审无法过
- 物理拓扑与逻辑拓扑混在一张图（物理 = 机房/机柜/网线；逻辑 = IP/VLAN/路由，分开画）
