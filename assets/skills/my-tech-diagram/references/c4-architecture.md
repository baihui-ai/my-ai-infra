# C4 架构图行业画法参考

> 供按需加载。C4 由 Simon Brown 提出，官方站点 c4model.com。
> C4 是「notation independent」的：不强制形状与颜色，但行业惯例（官方示例 + Structurizr 默认配色）已高度统一，下列默认配色可直接采用。

## 总览：四个层级（自顶向下逐级放大）

| 层级 | 回答的问题 | 受众 | 粒度 |
|---|---|---|---|
| 1. System Context | 系统在世界中的位置：谁用它、它依赖谁 | 所有人（含非技术干系人） | 整个系统 = 一个框 |
| 2. Container | 系统由哪些可部署/可运行单元组成 | 架构师、开发、运维 | 应用、数据库、队列等 |
| 3. Component | 某个 Container 内部的模块结构 | 该 Container 的开发团队 | 模块/服务/控制器 |
| 4. Code（可选，一般用 UML 类图） | 类级实现细节 | 开发 | 类/接口 |

辅助图：**Dynamic**（用 C4 元素画的时序图）、**Deployment**（容器到基础设施的映射）、**System Landscape**（企业内多系统全景）。

不必四层全画——官方建议 **Context + Container 对大多数团队已足够**；Component 只在重点模块按需画。

---

## 1. System Context Diagram

### 用途与适用场景
展示「你的系统」与「用户」和「外部系统」的关系总览。**给非技术人员看的入口图**，也是所有架构文档的第一张图。

### 元素与视觉约定

| 元素 | 默认配色（Structurizr） | 画法 |
|---|---|---|
| Person（用户/角色） | 深蓝 `#08427B` | 矩形（或带小人图标），白字 |
| Software System（本系统，焦点） | 蓝 `#1168BD` | 圆角矩形，居中放大 |
| Software System（外部系统） | 灰 `#999999` | 圆角矩形 |

每个框内三行：**名称** / `[类型: 如 Software System]` / 一句话职责描述。

### 关系与连线约定
- 实线箭头 + **必须标注**：意图 + 方向，如 `查看账户余额 [HTTPS]`。
- 关系线单向绘制；避免只写 "Uses" 这种无信息词。

### 布局规则
- 本系统居中，用户在上/左，外部系统在下/右。
- 元素总数 ≤ ~10；不画任何容器/技术细节。

### 门禁：最小信息清单
- [ ] 图标题含类型与范围（如 "System Context diagram for XXX"）
- [ ] 本系统一个框 + 名称与一句话职责
- [ ] 所有直接交互的用户角色（Person）
- [ ] 所有直接交互的外部系统
- [ ] 每条关系线有意图标注

### 常见错误
- 在 Context 图画出 Web App / Database 等容器细节（那是下一层的事）
- 关系线无标注或只写 "Uses"
- 元素过多，退化成系统全景图（多系统请改用 System Landscape 图）

## 2. Container Diagram

### 用途与适用场景
放大本系统，展示内部的可部署/可运行单元（Container 指「可独立部署运行的单元」，**不是** Docker）。**架构评审与技术方案的核心图**。

### 元素与视觉约定

| 元素 | 默认配色 | 画法 |
|---|---|---|
| Container（本系统内） | 浅蓝 `#438DD5` | 矩形，标注技术栈 |
| Database / Storage | 同浅蓝 `#438DD5` | **圆柱体** |
| 外部系统 | 灰 `#999999` | 圆角矩形 |
| Person | 深蓝 `#08427B` | 同 Context 图 |
| System Boundary | 虚线大框 | 包围本系统全部容器，标注系统名 |

Container 框内三行：**名称** / `[Container: 技术栈，如 Spring Boot / React / PostgreSQL]` / 一句话职责。

### 关系与连线约定
- 每条线标注 **意图 + 协议/技术**：`读写数据 [JDBC]`、`调用 API [JSON/HTTPS]`、`投递消息 [Kafka]`。
- 跨边界（访问外部系统）的线必须画到外部系统框，不可省略。

### 布局规则
- System Boundary 居中；用户与外部系统放边界外。
- 主调用流向尽量一致（如自上而下）。
- 容器数 ≤ ~12；超过说明该拆子系统画多张。

### 门禁：最小信息清单
- [ ] System Boundary 框与系统名
- [ ] 每个 Container 的名称 + 技术栈 + 一句话职责
- [ ] 每条关系线标注意图与协议/技术
- [ ] 外部系统与用户在边界外正确呈现
- [ ] 图例（key/legend）说明颜色与形状含义

### 常见错误
- 容器不标技术栈（`Web App` 不如 `Web App [React]`）
- 把「逻辑模块」画成容器（模块属于 Component 层）
- 漏画数据流向，只画调用不画读写

## 3. Component Diagram

### 用途与适用场景
放大**某一个** Container，展示其内部组件及职责分工。判断标准：**当某个容器内部结构复杂到需要向团队解释分层/模块边界时才画**（如核心服务的 Controller / Service / Repository 划分）。

### 元素与视觉约定

| 元素 | 默认配色 | 画法 |
|---|---|---|
| Component | 更浅蓝 `#85BBF0` | 矩形，框内三行：名称 / `[Component: 技术，如 Spring Service]` / 职责 |
| Container Boundary | 虚线大框 | 包围该容器的全部组件，标注容器名 + 技术 |
| 其他 Container / 外部系统 | 保持上一层颜色 | 作为边界外的交互对象出现 |

### 关系与连线约定
- 标注意图为主（`调用`、`派发任务到`），组件间多为进程内调用，不必强行标协议；跨容器调用仍要标协议。

### 布局规则
- 按分层排列（接口层 → 应用层 → 领域层 → 基础设施层，自上而下）。
- 组件数 ≤ ~20；只画当前容器，其他容器压缩成边界外的框。

### 门禁：最小信息清单
- [ ] Container Boundary 标所属容器名
- [ ] 每个 Component 的名称 + 技术 + 职责
- [ ] 组件间关系标注意图
- [ ] 跨容器调用标明目标容器与协议

### 常见错误
- 为每个容器都画组件图（只对复杂核心容器画）
- 组件粒度过细退化成类图（类级细节交给 Code 层/IDE）
- 组件职责描述为空或写成名字的同义重复

## 4. Dynamic Diagram（动态图）

### 用途与适用场景
用 C4 元素表达**运行时交互顺序**——相当于「C4 版时序图」。判断标准：**要在架构文档里说明某个关键场景（如下单、登录）跨容器/系统的调用顺序时用它**，替代 UML 时序图以保持元素一致。

### 元素与视觉约定
- 元素复用上一层级的框（Person / Container / Component），水平排列，**不画生命线和激活条**。
- 交互用编号箭头：`1. 提交订单 [HTTPS]`、`2. 扣减库存 [Kafka]`，编号即顺序。
- 并行交互用小数编号（`2.1`、`2.2`）或文字注明。

### 门禁：最小信息清单
- [ ] 场景名称（一个图一个场景）
- [ ] 编号的消息序列，方向与元素归属正确
- [ ] 关键消息标注协议/技术

### 常见错误
- 一张图塞多个场景；超过 ~15 步就该按子流程拆分

## 5. Deployment Diagram（部署图）

### 用途与适用场景
展示 Container 部署到哪些基础设施节点。**给运维/SRE 看的环境拓扑图**；常用于说明生产环境架构、可用区分布。

### 元素与视觉约定

| 元素 | 画法 |
|---|---|
| Deployment Node | 嵌套矩形（如 `AWS → Region → EC2 实例` 逐层嵌套），标注 `[Deployment Node: 环境/技术]` |
| Container Instance | 节点内的容器框，注明实例数（如 `x2`） |
| 基础设施节点（LB、DNS） | 普通节点 |

### 关系与连线约定
- 节点间连线标注协议与端口，如 `HTTPS 443`、`gRPC 50051`。

### 门禁：最小信息清单
- [ ] 标明环境（production / staging）
- [ ] 节点层级与实例数量
- [ ] 关键链路协议与端口

### 常见错误
- 与 Container 图重复信息量过大（Deployment 图只需回答「跑在哪、几份、怎么连」）

---

## 通用约定（所有层适用）

1. **每张图必须有标题**（含图类型与范围）和 **key/legend**（解释颜色、形状、线型）。
2. **每条关系线必须标注**，且避免 "Uses" 之类的单词式标注；跨容器关系标注技术/协议。
3. 配色不强制，但全文档内保持一致；兼顾黑白打印与色盲（形状与文字要独立可读）。
4. 图要能**脱离叙述独立看懂**；缩写要么不用要么在图例解释。
5. 元素框内标准三段式：**名称 / [类型: 技术] / 一句话职责**。
