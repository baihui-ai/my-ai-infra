# UML 图行业画法参考

> 供按需加载。按行业使用频率排序：Sequence > Class > Activity > State > Use Case > Component/Deployment。术语保留英文，来源基于 OMG UML 2.5.1 与 uml-diagrams.org 等行业惯例。

---
## 1. Sequence Diagram（时序图）— 使用频率最高

### 用途与适用场景
按时间顺序展示参与者/对象之间的消息交互。**判断：要说明「一次调用链路里谁先发、谁后发、谁等谁」时用它**；典型场景：API 调用链、跨服务交互、登录/下单等具体用例的实现过程。

### 元素与视觉约定
| 元素 | 画法 | 说明 |
|---|---|---|
| Participant / Actor | 顶部矩形框（Actor 画小人） | 名字下划线、格式 `name:Type`，匿名实例可省略 name |
| Lifeline（生命线） | 从框底垂直向下的虚线 | 表示对象在一段时间内存在 |
| Activation（激活条 / Execution Specification） | 生命线上的窄矩形条 | 表示该对象正在执行操作；自调用（self-message）用嵌套条 |
| 销毁 | 生命线末端的 **X** | 对象被销毁处 |

### 关系与连线约定
| 消息类型 | 线型 + 箭头 | 语义 |
|---|---|---|
| Synchronous（同步） | 实线 + **实心三角箭头** | 发送方阻塞等待返回 |
| Asynchronous（异步） | 实线 + **开口箭头（stick arrowhead）** | 发送方不等待；异步消息**没有** reply |
| Return / Reply（返回） | **虚线** + 开口箭头 | 同步调用的返回值，标注如 `result = query(id)`；可省略以降噪 |
| Create | 虚线 + 开口箭头指向新框 | 新对象创建 |

- **常见误区**：用虚线表示异步是错的——虚线是 return，箭头头型才区分同步/异步。

### 组合框（Combined Fragment）
| Operator | 语义 |
|---|---|
| `alt` | 多分支，仅守卫条件为真的分支执行（if/else），分支间用虚横线分隔 |
| `opt` | 单分支可选（无 else 的 if） |
| `loop` | 循环，守卫写迭代条件，如 `loop [for each item]` |
| `par` | 并行 |
| `ref` | 引用另一张时序图（拆大图用） |

### 布局规则
- 时间自上而下流逝；参与者从左到右按「发起者 → 主要参与者 → 次要/外部系统」排列。
- 消息文字写在箭头上方，动词开头（`createOrder()` 而非 `order creation`）。
- 一张图只讲一个用例/场景；超过 ~8 个参与者或消息嵌套超过 3 层就拆图（用 `ref`）。

### 门禁：最小信息清单
- [ ] 每个参与者的名称（且角色明确）
- [ ] 每条消息的名称/方法名
- [ ] 同步 vs 异步区分正确
- [ ] 关键返回值或状态变化标注
- [ ] 分支/循环条件用 alt/opt/loop 框标明守卫条件

### 常见错误
- 画成流程图（时序图的主体是「谁和谁交互」，不是算法步骤）
- 返回消息与异步消息箭头混用
- 把所有 getter/setter 都画上，噪音淹没主线

## 2. Class Diagram（类图）

### 用途与适用场景
展示系统的静态结构：类、接口、属性、方法及它们之间的关系。判断标准：**要说明「领域模型长什么样、谁拥有谁、谁继承谁」时用它**；典型场景：领域建模、DDD 实体关系、API 数据结构。

### 元素与视觉约定

类框为**三层矩形**：
```
┌─────────────────┐
│   ClassName     │  ← 类名（抽象类用斜体，接口加 «interface»）
├─────────────────┤
│ - id: Long      │  ← 属性层：可见性 名称: 类型
├─────────────────┤
│ + find(id): T   │  ← 方法层：可见性 名称(参数): 返回类型
└─────────────────┘
```
| 可见性符号 | 含义 |
|---|---|
| `+` | public |
| `-` | private |
| `#` | protected |
| `~` | package（默认） |

静态成员**下划线**，抽象方法斜体。

### 关系与连线约定（从强到弱）
| 关系 | 线型 + 箭头 | 语义 | 示例 |
|---|---|---|---|
| Composition（组合） | 实线 + **实心菱形**在整体端 | 强拥有，部分随整体销毁 | Order ◆— OrderItem |
| Aggregation（聚合） | 实线 + **空心菱形**在整体端 | 弱拥有，部分可独立存在 | Team ◇— Member |
| Inheritance / Generalization（继承） | 实线 + **空心三角箭头**指向父类 | is-a | Dog —▷ Animal |
| Realization / Implementation（实现） | **虚线** + 空心三角箭头指向接口 | 类实现接口 | Repo ⤏ IRepo |
| Association（关联） | 实线（可加开口箭头表导航方向） | 结构化引用，可标多重性 | User — Profile |
| Dependency（依赖） | 虚线 + 开口箭头 | 临时使用（参数、局部变量） | Service ⤏ Helper |

**多重性（Multiplicity）** 标在关联线两端：`1`、`0..1`、`*`（多）、`1..*`。
不确定聚合还是组合时优先用普通 Association——UML 社区公认 aggregation 语义模糊，滥用不如不用。

### 布局规则
- 父类/接口在上，子类在下；整体（菱形端）靠近组合的部分。
- 核心领域类居中，减少连线交叉。
- 一张图聚焦一个领域/模块，5~15 个类为宜；只画与主题相关的属性和方法，允许省略。

### 门禁：最小信息清单
- [ ] 每个类的名称
- [ ] 关键属性与方法（含可见性和类型）
- [ ] 类间关系类型正确（组合/聚合/继承/实现/关联/依赖）
- [ ] 关联两端多重性
- [ ] 接口用 «interface» 或棒棒糖符号标明

### 常见错误
- 把代码里所有字段方法全搬上来（类图是模型不是代码导出）
- 继承和实现箭头用反（继承实线、实现虚线，箭头都指向被继承/被实现方）
- 菱形方向画反：菱形永远在「整体」一端

## 3. Activity Diagram（活动图）

### 用途与适用场景
建模工作流/业务流程的步骤与分支，本质上是升级版流程图。判断标准：**要说明「一个业务流程从头到尾怎么走，含分支和并行」时用它**；典型场景：审批流、订单履约流程、批处理管线。

### 元素与视觉约定
| 元素 | 画法 |
|---|---|
| Initial Node（起始） | 实心圆 ● |
| Final Node（终止） | 牛眼 ◎（外圈套实心圆）；Flow Final 为 ⊗ |
| Action（动作） | 圆角矩形，写动词短语 |
| Decision / Merge（决策/合并） | 菱形 ◇，出边带守卫条件 `[condition]` |
| Fork / Join（分叉/汇合，并行） | 粗横条 ━━，一进多出为 fork，多进一出为 join |
| Swimlane（泳道） | 大矩形分区，顶部标角色/系统名 |
| Object Node（对象节点） | 矩形，表示动作间流转的数据（可选） |

### 关系与连线约定
- Control Flow：实线箭头，表示动作先后顺序。
- Decision 的每条出边**必须**有守卫条件且互斥完备（加 `[else]` 兜底）。
- Fork 后的并行分支最终用 Join 汇合（语义上是等全部到达，与 Merge 的「任一到」不同）。

### 布局规则
- 主流自上而下或自左而右一条主轴；分支向两侧展开。
- 泳道按职责划分（角色/系统/部门），一条泳道内的动作属于同一责任方。
- **连线不相交（硬规则）**：驳回/回流线统一走画布外侧通道（左缘或下缘），不与主流线交叉；多条回流汇入同一节点时，各自在不同高度水平汇入、最后一段共用，或先汇入合并菱形（merge）再一根线出去。发现交叉时优先移动节点位置，而不是硬拉线穿过去。
- 动作命名用动词开头（"校验库存"、"发送通知"）。

### 门禁：最小信息清单
- [ ] 唯一起始节点、至少一个终止节点
- [ ] 每个动作的名称
- [ ] 每个决策点的守卫条件（完备且互斥）
- [ ] 并行段用 Fork/Join 成对出现
- [ ] 跨责任方的流程用泳道划分

### 常见错误
- 决策菱形缺守卫条件或条件有重叠/漏洞
- 把 Fork 当 Decision 用（Fork 是无条件并行，Decision 是选一）
- 泳道划分到一半放弃，责任边界不清

## 4. State Diagram（状态机图）

### 用途与适用场景
建模单个对象在其生命周期内的状态变化。判断标准：**要说明「一个实体有哪些状态、什么事件让它迁移」时用它**；典型场景：订单状态、工单状态、连接状态机。

### 元素与视觉约定
| 元素 | 画法 |
|---|---|
| State（状态） | 圆角矩形，写状态名（名词/形容词，如 `待支付`） |
| Initial / Final | 与活动图相同：● / ◎ |
| Transition（转换） | 实线箭头，标注格式：**`触发事件 [守卫条件] / 动作`** |
| Composite State（复合状态） | 内含子状态的圆角矩形（分层用，可选） |

### 关系与连线约定
- 转换标注三段均可选，但**触发事件是主力**：`pay [余额充足] / 扣减库存`。
- 自转换（指向自身的箭头）表示事件不改变状态但执行动作。
- 状态内部可写 `entry / 进入动作`、`exit / 退出动作`、`do / 持续活动`。

### 布局规则
- Initial 在左上，终态在右下；主成功路径横向贯通，异常状态放下方。
- 状态命名避免动词（动词属于事件）。

### 门禁：最小信息清单
- [ ] 全部状态穷举且互斥
- [ ] 唯一 Initial；Final（若有）
- [ ] 每条转换的触发事件（守卫条件按需）
- [ ] 不存在「无入口」或「无出口」的悬空状态（终态除外）

### 常见错误
- 与活动图混用：状态图主体是「状态」，活动图主体是「动作」；对象生命周期用状态图，业务流程用活动图
- 状态爆炸：一层放不下时应上 Composite State 分层
- 漏掉异常/取消转换（如 `支付中 → 已取消`）

## 5. Use Case Diagram（用例图）

### 用途与适用场景
从用户视角描述系统提供的功能边界。判断标准：**要说明「谁用系统、能干什么、系统边界在哪」时用它**；典型场景：需求阶段的功能范围梳理、权限角色总览。**它只回答「做什么」，不回答「怎么做」**（怎么做交给时序图）。

### 元素与视觉约定
| 元素 | 画法 |
|---|---|
| Actor（参与者） | 小人图标，可以是用户、外部系统、定时器 |
| Use Case（用例） | 椭圆，内写动宾短语（「下单」「导出报表」） |
| System Boundary | 大矩形包围全部用例，顶部标系统名 |
| Association | 实线连接 Actor 与 Use Case（无箭头或简单箭头） |

### 关系与连线约定
| 关系 | 画法 | 语义 |
|---|---|---|
| `«include»` | 虚线箭头指向被包含用例 | 基用例**必然**执行被包含用例（公共步骤抽取） |
| `«extend»` | 虚线箭头**从扩展指向基用例** | 扩展用例**有条件地**插入基用例（可选分支） |

方向口诀：include 箭头指向「被用的公共块」；extend 箭头从「可选扩展」指向「主流程」。

### 布局规则
- Actor 放边界框外两侧，用例在框内。
- 主 Actor（发起者）在左，辅助 Actor（被调用的外部系统）在右。
- 一张图 ≤ 15 个用例，多了按子系统拆分。

### 门禁：最小信息清单
- [ ] 系统边界框与系统名
- [ ] 每个 Actor 的名称与角色
- [ ] 每个用例的动宾命名
- [ ] include/extend 方向正确
- [ ] 每个用例至少连接一个 Actor（或有 include 来源）

### 常见错误
- 用例写成界面操作（「点击按钮」不是用例，「管理库存」才是）
- 滥用 include/extend 把用例图画成流程图（用例之间没有先后顺序）
- Actor 之间乱连泛化以外的关系

## 6. Component / Deployment Diagram（简要）

### 用途与适用场景
- **组件图**：展示模块/组件及其接口（provided/required interface，棒棒糖与插座符号）。
- **部署图**：Node（三维立方体）表示服务器/设备，Artifact 部署在 Node 上，连线标通信协议。

**何时用 UML，何时用 C4**：描述**软件系统架构与上下文**优先用 C4（System Context / Container / Deployment 图对非 UML 读者更友好）；描述**单一模块内部的接口契约**或需要严格 UML 语义（如提供给建模工具的模型）时用 UML 组件图/部署图。实践中组件图常与 C4 Container/Component 图重叠，二者择一即可。

### 门禁：最小信息清单
- [ ] 每个组件/节点的名称
- [ ] 接口/通信关系标明（组件图标接口；部署图标协议）
- [ ] 部署图需标明运行环境（OS/容器/运行时）

### 常见错误
- 组件图退化成「方框连连看」，接口契约完全缺失
- 部署图不标协议，无法判断通信方式
