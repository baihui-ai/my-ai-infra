# DDD 相关图行业画法速查（Domain Model / Event Storming / Context Map）

## 选型速查

| 场景 | 画什么 |
|---|---|
| 表达同一设计范围内的核心类型、聚合/上下文边界及它们之间的关系 | 一张完整领域模型图（Domain Model） |
| 盘点领域命令与事件，即使输入是业务流程描述 | 一张按领域分组的领域事件图（无连线） |
| 盘点各模块有哪些命令/领域事件（交付文档、评审附件） | 分组式领域事件图 |
| 表达多个 Bounded Context / 团队 / 系统之间的集成关系与上下游依赖 | 限界上下文图 / Context Map |

本文件用于用户已确认的交付版式。领域模型按设计范围完整表达，领域事件按领域分组盘点，Context Map 表达集成关系；不因方法论粒度不同自动增加或拆分交付图。

# 一、领域模型图（Domain Model）

## 用途与适用场景

- 在同一张图表达设计范围内的领域类型与关系：Entity、Value Object、Aggregate 边界、领域服务、领域事件；多上下文用分区与限定名称区分。
- 用于设计评审、与领域专家对齐 Ubiquitous Language、代码结构设计的蓝本。
- **定位是沟通工具而非完整 UML 类图**：Vaughn Vernon《Implementing DDD》明确主张用 "UML sketch"——只画类型名与关系，不追求属性/方法完备。

## 元素与视觉约定

业界没有 ISO 式强制标准，以下是 Vernon 书、Microsoft DDD 指南、国内主流 DDD 教程中重合度最高的约定：

| 元素 | 视觉约定 | 说明 |
|---|---|---|
| Entity（实体） | 普通矩形，可标 `«Entity»` 或角标 **E** | 有唯一标识（ID），生命周期内可变 |
| Value Object（值对象） | 矩形标 `«Value Object»` / **VO**；常用不同底色（浅灰/浅蓝）或无边框样式区分 | 无 ID，不可变，靠属性值判等 |
| Aggregate / Aggregate Root（聚合/聚合根） | **虚线圆角矩形框**包住聚合内所有成员；聚合根用加粗边框或 `«Aggregate Root»` 标注 | 虚线边界是最关键的视觉元素，表达一致性/事务边界 |
| Domain Service（领域服务） | 矩形标 `«Domain Service»` / **DS**，常用圆角或斜体名 | 无状态，承载不属于任何实体的领域逻辑 |
| Domain Event（领域事件） | 矩形标 `«Domain Event»`，与分组领域事件图的绿色语义保持一致（用户另指定图例时除外） | 表示聚合内发生的事实 |
| Enumeration（枚举） | `«enumeration»`，可并入 Value Object 样式 | 简单取值集合 |
| Repository（仓库，可选） | 一般**不画**进领域模型图；如需表达，放图边缘标 `«Repository»` | 属于接口/技术关注点 |

颜色不是强制的；团队自定义图例时，至少要把「Entity vs Value Object」和「Aggregate 边界」两对区分开。

## 关系与连线约定

- **关联（Association）**：实线连接，标注角色名与多重性（`1`、`0..1`、`1..*`、`*`）。跨聚合的关联一律通过 ID 引用表达——线上标注 `ID 引用` 或用虚线区别于聚合内实线。
- **聚合内包含**：聚合根到成员实体/值对象的实线，表示组合关系（可理解为强关联）。
- **继承（Inheritance）**：空心三角箭头指向父类；DDD 建模中慎用，出现时优先质疑是否该拆成组合。
- **依赖（Dependency）**：虚线箭头，常用于「聚合根 --发布--> Domain Event」「Domain Service --使用--> 聚合」。
- **重点约定（区别于 UML 类图）**：**模型图默认只保留类型名与关系，不画属性与方法**。理由是属性/方法属于实现细节，会让图迅速过期、干扰结构讨论。核心业务不变量写在关系模型说明中，不扩展为字段/方法卡片。用户未要求时不额外生成 ER 图或详图。

## 布局规则

- 每个 Aggregate 一个虚线框，聚合根放在框内左上或中心位置。
- 核心聚合（Core Domain 相关）放图面中心，外围是支撑性聚合。
- 跨聚合连线尽量少、尽量只有 ID 引用虚线；连线交叉多说明聚合划分可能有问题。
- 同一设计只画一张完整图，不按 Bounded Context 拆图，也不附加局部详图。多个上下文在同一画布分区，区域标题保留上下文名称；区内再画聚合边界。跨区关系按用户确认的语义保留，不把上下文分区当作同一事务边界。
- 核对节点/关系清单后分配分区和连线通道；密集内容扩大画布或在同图换行，不能缩字、删减或拆文件。

## 推荐版式：双语卡片式实体关系图（中文团队实践）

中文团队的领域模型交付图常用「双语卡片 + 多重性直连线」版式（参考 `../assets/domain-model-cn-er.jpg`），它比 UML 类图轻、比纯文本框信息密度高：

- **卡片双行结构**：上行英文类名（加粗，如 `Contract`），下行中文业务名（如「合同」），中间一条细分隔线。**只保留这两行**——不画属性/方法，与「只保留类型」约定一致。
- **颜色按域/模块分组**：同一大模块的卡片用同一色系（参考图中权限/组织域绿色系、业务域黄色系），边框用同色系深色。色相从所选风格色板派生（如 Claude 风用赭橙/暖棕/橄榄等暖色区分域），颜色即分组，必须配图例。
- **关系线**：直线连接，**两端都标多重性**（`1`、`0..1`、`1..*`、`0..*`），不画箭头/菱形；聚合边界如需表达仍用虚线框。
- **布局**：中心辐射式——核心实体（如 合同、项目）放中心，关联实体环绕，避免长距离斜线。
- **反面教训**（参考图自身的问题，生成时必须避免）：英文类名过长导致换行断裂（`ContractCooperationAgreeme nt`）。规则：**卡片宽度按最长行文字 + 左右各 ≥12px padding 计算，英文长名优先加宽卡片或换行按单词边界断，绝不从单词中间断开**。

## 命名规范

- 全部使用 Ubiquitous Language，与代码中的类名一致（`Order`、`OrderLine`、`Money`）。
- 中文团队：图上可用中文名 + 英文类名双行（如「订单 Order」），代码侧以英文为准。
- Aggregate Root 命名即业务名，不加 `Aggregate` 后缀。

## 门禁：最小信息清单

- [ ] 明确整张图的设计范围；若含多个领域/上下文，分区归属和同名概念的限定名称已确定
- [ ] 已识别出全部 Aggregate 及各自的 Aggregate Root
- [ ] 每个成员对象已判定为 Entity 还是 Value Object（判据：是否有独立 ID / 是否可独立存在）
- [ ] 聚合间引用方式已确定（ID 引用，不允许跨聚合对象引用）
- [ ] 关键多重性已确认（1:N / M:N 是否真实存在，M:N 是否该拆）

缺任一项就先回到建模讨论，不要画图。

## 常见错误

- 把 UML 类图原样搬来：堆满属性、getter/setter，图变成代码截图。
- 聚合边界缺失：一堆框和线，看不出一致性边界，等于没画。
- 跨聚合直接对象引用连线（Order → Customer 实线），破坏聚合独立性。
- 将多个上下文混成一个边界导致同名概念歧义；正确方式是同图分区与限定命名，不是自动拆图。

# 二、事件风暴图（Event Storming）

## 用途与适用场景

- Alberto Brandolini 于 2013 年提出的协作建模工作坊方法，用于快速还原业务流程全貌、发现领域事件、推导出 Command / Aggregate / Bounded Context。
- 三种粒度：Big Picture（全流程探索）、Process Level（流程建模）、Design Level（细化到聚合，接近编码）。

## 元素与视觉约定

### 交付约定与方法论背景

本 Skill 的“领域事件图/事件风暴图”采用用户参考图的分组盘点版式，不采用工作坊时间轴。先实际查看 `../assets/event-storming-cn-grouped.png`。

默认语义：黄色便签是命令、绿色便签是事件、粉色标题条是领域分组；卡片有文字类型标注。命令在左、事件在右，空间配对表达对应关系；不能因排版成对而补造命令或事件。画图前按 `event-semantics.md` 核验业务事实。参与者、策略、外部系统等输入事实记录在关系模型中，不擅自把本图扩展为 Actor → Command → Aggregate → Event 的流程。

Brandolini 工作坊常用橙事件/蓝命令，但那是背景知识，不覆盖本 Skill 的默认配色与布局。只有用户点名该配色才改变色板；换色不自动改成时间轴。用户明确要流程顺序时使用流程图/活动图；仅仅输入含“然后/之后/成功后”等时序词，不是改变图型的指令。

## 布局模式：分组式领域事件图（唯一默认模式）

**事件风暴图默认且仅默认分组式**：把命令/事件按领域/模块聚成一块一块的（结构参考 `../assets/event-storming-cn-grouped.png`）。即使输入是一段流程描述，也先按涉及的领域/模块拆分归组。

**本图不画任何连线**：组间不画、组内命令→事件之间也不画——「命令在左、事件在右成对平铺」的空间位置本身就是关系表达。分支、先后、因果一律不出现在图上；用户要流程顺序时，说明他要的是流程图或 UML 活动图，路由到 `pm-and-other-diagrams.md` 的流程图节或 `uml-diagrams.md` 的活动图节，绝不要把事件风暴图画成流程图。

- **顶部分组标题条**：一个条 = 一个领域/模块分组（如 项目、合同、用户、权限），组名居中；标题条贯穿该组列宽。
- **组内纵向成对**：命令在左、事件在右，一对一行，行间距一致、整齐平铺；查询没有领域事件时允许命令列单贴；无显式命令的真实事件允许在事件列单贴并注明触发来源；一个命令触发多个事件时向右并列展开。
- **类型标注必须文字化**：每张卡片/便签上用小字标注「命令」或「事件」（放在名称上方一行），不靠颜色猜语义。
- **视觉跟随所选风格**（见 `visual-styles.md`）：
  - **便签风**（事件风暴的天然搭配）：黄色便签 = 命令、绿色便签 = 事件、粉色宽条 = 领域分组，右上角折角；这正是参考图的中文圈变体配色。
  - 简洁/Claude/科技风：命令/事件用该风格色板的两个可区分层级（如事件用强调色描边浅底、命令用中性底），分组标题条用主色浅底，卡片样式不带折角。
  - 仅当用户点名「Brandolini 官方配色」时才用橙=事件/蓝=命令那套——此时图例必须随图给出。
- 组间不画连线。

## 命名规范

- **Event：过去式，陈述已发生的事实**。英文用 `名词 + 动词过去分词`：`OrderCreated`、`PaymentReceived`；中文对应「名词 + 已 + 动词」的完成式：**订单已创建、库存已扣减、支付已成功**。
- **Command：现在时，表达意图，可被驳回**。英文用 `动词 + 名词`：`CreateOrder`、`CancelOrder`；中文用**动宾结构**：**创建订单、取消订单、查询产品、登录系统**。
- 中英文词序恰好镜像：`CreateOrder → OrderCreated` 对应「创建订单 → 订单已创建」。同一张图上不要混用时态：看到「订单创建」这种无「已」字的事件贴，要追问到底是命令还是事件。
- 命名必须有业务含义，用 Ubiquitous Language；禁止技术味命名（`RecordInserted`、「数据已保存」）。
- 区分粒度：「支付已成功」是事件，「支付已开始/已结束」通常是过程噪音，不算领域事件。

## 门禁：最小信息清单

- [ ] 设计范围、领域/模块分组已明确（可由用户提供的代码/文档确定）
- [ ] 命令、对应事件及一对多关系已明确；查询可无事件，定时/外部事实触发的事件可单贴并标明来源
- [ ] 命令/事件名称和归属有来源，不能根据一般业务经验补造

不要求真实工作坊到场记录、不设最低事件数量；默认颜色和版式已在本 Skill 确定，不需要用户重复确认。

## 常见错误

- 事件用现在时/祈使句命名（把「创建订单」当成事件贴），命令与事件混淆。
- 变成开发自嗨：用技术语言贴事件，领域专家看不懂、无法纠错。
- 将用户提供的流程描述直接画成时间轴或带箭头的因果链，违背分组盘点版式。
- 混用工作坊官方配色与本图黄命令/绿事件配色，或缺少类型文字标注。

# 三、限界上下文图 / 上下文映射图（Bounded Context / Context Map）

## 用途与适用场景

- 战略层视图：表达多个 Bounded Context 之间的集成关系、团队权力关系与上下游方向。
- 用于微服务边界设计、遗留系统集成决策、团队间协作约定评审。

## 元素与视觉约定

| 元素 | 视觉约定 | 说明 |
|---|---|---|
| Bounded Context | 大矩形/圆角矩形，内部写上下文名；可内嵌简化的核心聚合名 | 一张图的节点 |
| 子域类型标注 | 在上下文框角标或名称下标注 `Core` / `Supporting` / `Generic` | **业界常见做法**，Microsoft 与多数 DDD 教程推荐在 Context Map 上标注子域分类，帮助对齐投资优先级；不是强制 |
| 团队归属（可选） | 框下注明负责团队 | Context Map 同时是团队关系图 |

## 关系与连线约定

连线上标注关系模式缩写，**U = Upstream（上游，影响方）、D = Downstream（下游，受影响方）**，箭头惯例：实线箭头从 D 指向 U 或在线两端直接标 `U`/`D` 字母（Evans 原书惯例是端点字母标注，二选一、全图统一）。

对称关系（无上下游）：

| 模式 | 缩写 | 含义 |
|---|---|---|
| Partnership | P | 双向依赖，共成败，发布需协调；慎用 |
| Shared Kernel | SK | 共享一小份子模型/代码（如 `Money`），改动须双方同步；保持小 |

上下游关系：

| 模式 | 缩写 | 含义 |
|---|---|---|
| Customer-Supplier | C/S | 上游配合下游：下游提需求、上游排期兼顾 |
| Conformist | CF | 下游无话语权，原样照搬上游模型（典型：接遗留 ERP、政府/第三方强势 API） |
| Anti-Corruption Layer | ACL | 下游自建翻译层，隔离上游混乱模型，保护本方领域语言 |
| Open Host Service | OHS | 上游提供标准化协议/API（含版本化）服务多个下游 |
| Published Language | PL | 配合 OHS 的标准交换格式/契约（OpenAPI、Protobuf、行业报文标准） |
| Separate Ways | SW | 刻意不集成，重复比耦合便宜 |
| Big Ball of Mud | BBoM | 边界腐烂的遗留泥球，用斜线/警示标出，接它必加 ACL |

决策口诀：下游能否影响上游？不能 → 模型合用就 CF、不合用就 ACL；能 → C/S，多个消费者再加 OHS + PL。

## 布局规则

- Core 子域的上下文放图面视觉中心，Supporting / Generic 在外圈。
- 上游画在上方或左方、下游在下方或右方，让 U→D 的影响方向在视觉上自上而下。
- 连线只画真实存在的集成关系，不画「概念上相关」的线。
- 系统级 Context Map 控制在 5-15 个上下文；更大规模分层出图。

## 推荐版式：分带卡片式（交付文档首选，替代「泡泡图」）

经典 Context Map 常见失败形态是「泡泡图」：一堆椭圆/圆角泡 + 手绘虚线边界 + 游离文字标签，没有关系线——它只回答了「有哪些分组」，回答不了「谁影响谁、怎么集成」。评审/交付场景推荐分带卡片式（示例：`diagrams/context-map-demo.svg`）：

- **横向分带 = 子域分类**：核心域 / 支撑域 / 通用域三条横带（浅灰底 + 左侧带名 + 一句定位语），投资优先级一目了然，替代框角小字标注。
- **上下文 = 统一尺寸卡片**：中文名 + 英文名的双行卡片 + 一句话职责；卡片对齐到网格、等距平铺。**实体不进入本图**（实体属于各领域模型图），否则粒度混叠。
- **箭头方向 = 影响方向**：上游 → 下游画实线箭头，淘汰 U/D 字母标注（读者不用再查约定）。
- **关系线按模式类别配色 + 中文全称标注**：协作类（Partnership / Customer-Supplier）绿色、标准接口类（OHS / PL）蓝色、被动跟随类（Conformist）橙色警示、隔离（ACL）紫色且在下游框边缘画小梯形。标注写「供需配合 C/S」而不是孤零零的「C/S」。
- **对称关系**（Partnership、Shared Kernel）用双向箭头。
- 游离标签禁止：所有文字必须锚定在卡片/线/带上。

## 命名规范

- 上下文名用业务域名词：`订单上下文 Order Context`、`计费 Billing`，不用技术名（`订单服务DB`）。
- 关系标注用标准缩写（P、SK、C/S、CF、ACL、OHS、PL、SW），团队内统一一张图例。
- ACL 实现为具体组件时，在下游框边缘画出小梯形/小框标注 `ACL` 即可。

## 门禁：最小信息清单

- [ ] 全部相关 Bounded Context 已识别并命名（含遗留/外部系统，外部系统标 External）
- [ ] 每对上下文之间的集成方向已确认（谁是 U、谁是 D，依据：谁的变化会迫使对方改）
- [ ] 每条关系已选定模式（按决策口诀走一遍，不允许只画线不标模式）

## 常见错误

- 只画方框连线不标关系模式和 U/D，退化成普通系统架构图。
- 把 Bounded Context 等同于微服务/应用，一个上下文拆成多个节点或反之。
- 接 Big Ball of Mud 不加 ACL，遗留概念渗进核心域。
- 图长期不更新：团队重组、契约变更后 Context Map 已失真却无人维护。
