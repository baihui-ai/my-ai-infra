# 关系模型：订单支付时序图（payment-sequence）

- 图类型：UML Sequence Diagram（时序图）
- 风格：科技炫酷风（tech，用户指定）
- 场景：用户通过前端 App 使用支付宝完成订单支付，含异步回调与前端轮询确认

## 参与者（从左到右：发起者 → 主要参与者 → 外部系统）

| 参与者 | 类型标注 | 说明 |
|---|---|---|
| 用户 | «actor» | 支付发起人，画小人 |
| 前端 App | «frontend» | 客户端应用 |
| 订单 API | «service» | 后端订单服务 |
| 支付宝 | «external system» | 外部支付平台 |

## 消息时间序（自上而下）

| # | 发送方 → 接收方 | 消息 | 类型 | 备注 |
|---|---|---|---|---|
| 1 | 用户 → 前端 App | 点击支付 | 同步（实线+实心三角） | 触发流程 |
| 2 | 前端 App → 订单 API | createPayment(orderId) | 同步 | 创建支付单 |
| 3 | 订单 API → 前端 App | paymentNo | 返回（虚线+开口箭头） | 关键返回值：支付单号 |
| 4 | 订单 API → 支付宝 | tradePay(paymentNo) | 同步 | 向支付宝发起支付 |
| 5 | 支付宝 → 订单 API | 受理成功 | 返回（虚线+开口箭头） | 同步受理结果（受理 ≠ 支付结果） |
| 6 | 支付宝 → 订单 API | notify（支付结果） | 异步（实线+开口箭头） | **异步回调，关键路径**，发送方不等待、无 reply |
| 7 | 订单 API → 订单 API | 更新订单状态：待支付 → 已支付 | 自调用 | 状态变化标注 |
| 8 | 前端 App → 订单 API | queryPaymentResult(paymentNo) | 同步 | 在 loop 框内 |
| 9 | 订单 API → 前端 App | 支付成功 | 返回（虚线+开口箭头） | 在 loop 框内 |
| 10 | 前端 App → 用户 | 展示支付成功 | 返回（虚线+开口箭头） | 收尾 |

## 组合框

- `loop [每 2s 轮询一次，直至拿到支付成功或超时退出]`：包围消息 8、9（前端 App 与 订单 API 生命线段）

## 激活条（Activation）

- 前端 App：消息 1 到达起 → 消息 10 结束（长激活，含轮询段）
- 订单 API：消息 2 → 消息 7（创建支付单、发起支付、处理回调连续段）；轮询查询处再一段短激活
- 支付宝：消息 4 → 5 一段；发出异步回调（消息 6）处一小段

## 假设与简化（已在图中注明，非编造内容）

- 消息 5「受理成功」：同步调用支付宝的即时返回是受理结果而非最终支付结果，最终支付结果以异步回调（消息 6）为准——这是任务描述「支付宝异步回调支付结果」的直接语义。
- 轮询守卫条件「每 2s 轮询一次，直至拿到支付成功或超时退出」：任务只说明「前端轮询拿到支付成功」，间隔与超时退出为常规轮询语义的补全标注，属守卫条件的合理写法。
- 订单 API 激活条将「创建支付单 / 发起支付 / 处理回调」画为一段连续激活，简化了「先返回支付单号、再发起支付」之间可能的内部调度细节。
