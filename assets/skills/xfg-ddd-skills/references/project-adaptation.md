# 项目适配与执行边界

## 新项目与存量项目

- 新建 Java 项目默认采用本套 DDD 六边形架构。在技术方案阶段先明确领域与聚合边界、模块职责及依赖方向，采用 Trigger/API/Case/Domain/Infrastructure 的职责划分，按真实需求保留最小必要模块；需求尚未涉及的中间件和复杂模式不预建。
- 存量 Java 项目先查真实包结构、调用链、业务边界和基础设施。包括没有 DDD 的项目，都学习并采用适用的代码规范：明确类型和命名、方法单一职责、业务编排与数据访问分离、复用与异常语义。保持已有分层和框架，不因引用本规范自动迁移目录、拆 Maven 模块或替换 JPA/MyBatis。
- 当前用户需求、目标项目有效契约与本项目 Java 约定优先；上游的“唯一正确目录”、按分支数量选模式、60行等阈值均只作为该套架构示例。新项目选定该架构后保持一致；已有不同架构按实际职责映射，不把包名不同直接判错。

## 技术方案先设计好

新建 Java 项目的方案必须能指导实现，至少说明以下实际适用内容；存量方案给出既有结构、变化部分及适配依据，无关部分可简述无变化：

1. 模块/包结构、依赖方向、入口、Case 编排、Domain 业务规则与 Infrastructure 实现的职责；列出实际文件或拟新增位置。
2. 领域/聚合边界、实体/值对象、状态与不变量，关键 Request/Response/DTO 和接口签名；通过代表性逻辑展开业务规则和失败分支。
3. 单域服务与跨域流程、仓储/外部端口的接口归属和实现、事务边界、并发/幂等与必要的失败恢复；避免把业务校验散落在 DAO 或控制器。
4. 真实可复用的框架、老方法和工具；表结构六基础字段、语义合理的默认值、查询/索引依据、有界分页与批量访问沿用本项目 Java 约定。
5. 功能默认生效方式、适用验证和实施任务；明确需求或可操作恢复依据之外不新增开关。架构模式选型给出当前需求理由，不以预留扩展代替设计。

## 代码学习与冲突处理

- 使用 import 与类简名，固定字段协议采用明确类型；内部动态索引 Map 允许。命名和类型风格沿用目标 JDK、框架和项目约定。
- 控制流遵循[本项目 Java 控制流约定](../../my-create-feature/references/java-dev.md#控制流与条件表达式)：if/else及for语句体始终加花括号，代码块（含try/catch/finally和方法体）统一多行书写，if条件达到3个独立判断项时提取业务谓词，保留短路和求值顺序；原始示例不覆盖此规则。
- 主方法表达业务步骤，提取承担清晰职责的方法；采用模式应减少具体复杂度，不为少量 if 或固定校验新增等价抽象。已有成熟服务、Repository/Mapper、事务、分页、工具能力优先复用。
- SQL、审计字段、默认值和索引分别按目标项目证据核对。上游示例的 OFFSET、字段、框架或 Lombok 不覆盖本项目已有的索引、游标分页、六基础字段和类型规范。

- 业务失败优先复用目标项目已有业务异常/错误码，遵循[业务异常约定](../../my-create-feature/references/java-dev.md#业务异常与错误码)；保留 cause、边界映射、事务和重试语义，不为每个失败新增异常类，不将系统故障机械转成业务拒绝。

- 事务采用[按需使用约定](../../my-create-feature/references/java-dev.md#事务按需使用)：默认不新增业务事务，方案先说明必要性；不为DDD分层或JPA惯例全类添加Transactional，也不删除保障原子性/锁及框架写入所需的最小事务。

## 脚本与部署

源码脚本为可选建项工具，随包保存但安装/加载不执行。仅在明确创建新工程、目标位置与参数已确定时使用；不得向当前业务仓库默认生成工程、修改全局 Maven 配置或启动容器。原脚本会下载并运行远程 Maven Archetype，且非交互模式有默认参数，不能把它当只读检查或随意试运行。部署需相应用户指令与实际环境依据。

脚本的 Bash 语法检查与资源装配可独立验收；真实 Maven 模板生成、Windows 运行和生产部署在未执行时明确保留未验证。
