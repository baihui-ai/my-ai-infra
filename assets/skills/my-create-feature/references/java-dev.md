# Java 开发规范（java-dev）

本规范由本项目统一维护，融合已确认的开发经验，面向 Java 变更按需加载。项目已有契约与用户明确要求优先；冲突须说明，不静默改变现有 API、分页基准或依赖版本。非 Java 任务跳过。

## 架构与代码设计

涉及 Java 时检查内置 `xfg-ddd-skills` 是否可用；可用则读取其[项目适配](../../xfg-ddd-skills/references/project-adaptation.md)及本次相关代码规范。新建 Java 项目默认采用该套 DDD 六边形架构，技术方案先明确领域/聚合、模块依赖、类型/接口、编排与事务、仓储/端口及数据访问；存量项目包括非 DDD 项目均学习适用代码规范，沿用已有结构和框架。缺少资源则记录缺口，不伪造已加载或通过；不因加载规范执行建项或部署。

## 实现与复用

- 使用 import 和类简名；同名类型冲突时允许必要的全限定名，不在业务代码中反复书写包名。
- 业务入参、出参使用职责清晰的 Request、Response、DTO、VO 或项目已有类型。避免用 Map<String, Object> 隐藏固定字段契约；动态键值协议可保留 Map 并说明边界。内部按 ID 索引批量查询结果的 Map 正常使用。
- 每个方法承担一个清晰职责；主方法表达业务步骤，复杂步骤提取为有业务含义的方法。避免为了行数拆成无意义的转发层。
- 编写前查找已有同类方法、框架与工具，记录实际复用入口。优先使用项目现有 JPA、MyBatis、事务、分页和校验能力；新增实现说明既有能力为何不足，不另造等价框架。
- 优先复用成熟工具类，如项目已有 Apache Commons Lang 时使用 StringUtils.isBlank。允许引入确有必要的新包，说明用途、与现有能力的重叠、版本兼容及许可证，按项目依赖约定更新；不为一次简单判断强行新增依赖。
- 命名、包结构、成员组织、日志和异常处理沿用项目风格；日志参数化，异常保留原因和业务上下文，资源及时关闭，避免吞异常和泄露凭据。

## 控制流与条件表达式

- `if`、`else if`、`else` 及 `for`（普通循环和增强循环）的语句体始终用 `{}` 包裹，只有一条 `return`、`throw`、`continue` 或其他语句也必须加块；保持正常 `else if` 链，无需额外制造嵌套层。不要生成 `if (condition) return value;` 或 `for (...) handle(item);`。
- 代码块统一多行书写：if/else、for/while/do、try/catch/finally（含 try-with-resources）、switch、方法体及块形式 lambda 等，左花括号后换行，真实语句单独成行并按项目规范缩进，右花括号单独占一行；相邻的 `} else {`、`} catch (...) {`、`} finally {` 可按项目格式衔接。禁止 `try { work(); }`、`catch (...) { throw error; }`、`if (...) { return value; }` 等单行代码块。有意为空的块也展开，不为排版添加虚假语句或吞掉异常；对象/数组初始化、字符串或 JSON 字面量中的花括号按对应语法和项目格式处理，不视为控制流代码块。
- `if`/`else if` 条件有 **3 个及以上独立判断项** 时，提取为有业务含义、返回 boolean 的方法，主流程使用 `isEligible...`、`isMismatched...` 等明确谓词。1～2 项无需因数量提取，已有恰当业务谓词可继续复用。按 `&&`、`||` 组合的实际判断项计算，括号和换行不减少项数；已提取谓词的一次调用在调用点算一项，不递归展开其内部判断。
- 提取方法时保留原有运算符、括号分组、判断顺序、短路求值、空值保护、异常及副作用时机。优先传入判断需要的对象或上下文，在方法内按原顺序求值；不要把各判断先算成 boolean 实参，导致原本被短路跳过的 getter、远程调用或空对象访问提前执行。不为达到条数改变业务语义或生成无意义的参数转发。
- 设计中的代表性代码、实现与评审均遵循本节。评审检查新增/变更的控制流和复杂条件，不批量重写无关历史代码；原始第三方示例保留归档，新生成代码按本节调整。

```java
if (isMismatchedJob(job)) {
    throw new BusinessException(ErrorCode.JOB_MISMATCH);
}

private boolean isMismatchedJob(Job job) {
    return !expectedEnvironment().equals(job.env())
            || !expectedType().equals(job.jobType())
            || job.taskId() != 0;
}

for (Job job : jobs) {
    handle(job);
}
```


```java
String payload;
try {
    payload = mapper.writeValueAsString(new Payload(actor));
} catch (JsonProcessingException error) {
    throw new BusinessException(ErrorCode.JOB_REGISTRATION_FAILED, error);
}
```

以上为代码组织示意，BusinessException、ErrorCode及其构造器/枚举值均为示意名称，使用目标项目真实业务异常与错误码，不要求新增同名类型；序列化失败须按真实项目的系统错误/重试映射处理。具体类型和判断规则沿用目标项目；补块及提取方法不能改变原异常或返回值。

## 业务异常与错误码

- 业务规则校验、业务状态不允许、目标业务对象不存在等预期业务失败，优先复用目标项目已有业务异常（如 BusinessException、BizException、ServiceException、AppException）及对应错误码。先查真实异常类型、构造方式、错误码定义、全局异常处理器和相邻业务用法，使用项目实际契约；不直接用 IllegalArgumentException、IllegalStateException、Exception 或裸 RuntimeException 代替业务语义。
- 不为每个业务失败新增异常类，不另建一套错误码或异常体系。已有错误码含义不符时，按项目登记方式补充准确的业务码，不借用无关码求复用。项目缺少业务异常机制时在方案中明确最小统一方案，不臆造已存在的类或构造器。
- 业务异常的错误码、对外消息、HTTP/任务处理映射、事务回滚和可重试语义沿用现有约定；不将原可重试的系统故障转换为不可重试的业务拒绝，不因换异常类型破坏已有调用方契约。
- 数据库、IO、序列化和远程调用等底层异常按项目边界处理：需要转换时使用已有异常封装/工厂并保留 cause 和必要上下文；异常链不支持 cause 的问题须说明最小改动，不仅拼接 getMessage() 丢失堆栈。不为满足业务异常偏好在每层 catch/wrap，不把所有系统故障、编程错误或框架异常机械伪装为业务失败。框架按契约抛出的异常和基础设施内部必要的标准异常可保留，边界处统一映射。
- 修改异常时还需按[失败、重试与告警分类](delivery-lessons.md#1-失败重试与告警分开设计)核对处理器、切面与消费者，避免已确认业务拒绝重复告警或真实系统故障被包装掩盖。
- 设计与评审核对失败场景、实际异常/错误码、边界处理及回滚/重试影响；检查新增/变更代码，不批量替换无关历史异常。用户可见消息不暴露SQL、凭据或内部堆栈，日志保留排查依据。

## 类型与 Spring

- DTO 优先沿用项目已有 Lombok、record 或普通类风格及 JDK 版本；不强制引入 Lombok。JPA Entity 的 equals/hashCode、toString 和懒加载关系需单独设计。
- 使用构造器注入，保持依赖方向；拆分服务时检查循环依赖，优先提取共同职责，不默认用 @Lazy 掩盖依赖问题。
- 输入按业务规则校验必填、数值范围、枚举和分页上限，嵌套对象检查级联校验；沿用项目所用校验框架。
- 明确外部页码和内部框架页码的基准，只在边界转换一次；覆盖第一页和后续页，不能因 JPA 从 0 开始就改变已有外部接口。
- 并发更新采用适当的原子 SQL、乐观锁或锁机制；防重复操作由唯一约束等机制兜底。结合事务提交时机处理冲突，不能假定 save 时一定抛出唯一约束异常。
- 复用项目托管线程池，明确超时、异常传播和资源关闭；测试沿用已有框架，不强制升级 JUnit 或其他依赖。

## 事务按需使用

- 默认不新增业务层事务。普通列表/详情/统计查询、格式转换、纯计算、单条原子条件SQL或彼此允许独立成功的操作，先考虑无额外事务的实现；不因方法位于Service/Repository、使用JPA或“只读优化”而惯例添加类级/方法级 `@Transactional`，也不把 `readOnly=true` 当成不开事务。
- 只有明确需要多步操作原子提交/回滚、一致性快照、事务锁或框架必要写入语义时才保留/新增事务，并说明要保护的具体业务不变量。优先检查现有原子SQL、约束、版本机制及框架已有事务是否已经满足；不为“保险”重复套事务，也不擅自增加新框架来规避必要事务。
- “不新增业务事务”不等于数据库完全没有事务，不关闭框架/数据库正常的提交机制。JPA写入、flush、懒加载或锁等实际依赖事务的路径须按项目真实用法核对，不能机械移除注解造成写入失败、部分更新或丢失锁保护。存量事务先核对调用链、传播与回滚规则，仅修改本次范围内确属多余的部分。
- 确有必要时把事务压缩到最小数据库操作单元，采用项目已有机制，核对外层事务、实际代理调用和生效边界；数据库访问结束即提交/回滚。不要把远程调用、MQ等待、文件处理、大循环、批次间sleep或重试退避包在长事务中；不为每个查询默认创建独立事务或强行使用REQUIRES_NEW。
- 技术方案明确“是否需要事务、依据、边界”；实现和评审验证无额外事务是否仍满足契约，必要事务是否真实生效。多步转账、业务写入与需同成同败的outbox等不得为满足偏好而拆成部分提交；数据库事务也不能自动覆盖外部系统副作用，应沿用项目已有一致性方案。

## 表结构基础字段

- 新建业务表必须包含 `id`、`create_time`、`update_time`、`create_by`、`update_by`、`is_deleted` 六个基础字段，在设计的字段清单和建表 SQL 中明确体现。
- 类型、长度、可空性、默认值、主键生成、时间与操作人填充、逻辑删除取值沿用目标项目已有表、迁移和公共实体约定；先查真实依据，不自行统一成 bigint、datetime、0/1 或其他固定定义。约定不明或相互冲突时列出待确认项。
- 字段尽量设置符合业务语义的默认值；确定不允许缺失的字段优先使用 NOT NULL，并区分数据库 DEFAULT 与应用自动填充。沿用项目已有约定；没有合理默认值的必填字段通过校验要求显式提供，未知或未发生的数据保留真实语义，不用 0、空字符串、虚假操作人或时间掩盖缺失。默认值变更须核对存量数据及写入兼容性。
- 默认值、可空性与索引设计分别核验，不能认为设置 DEFAULT 或 NOT NULL 就能防止索引失效。MySQL 的 IS NULL 查询也可能利用索引，参见 [MySQL 官方说明](https://dev.mysql.com/doc/refman/8.0/en/is-null-optimization.html)。索引利用仍依实际查询、数据分布和 EXPLAIN 判断，不为规避 NULL 在索引列上包裹 IFNULL/COALESCE 等表达式。
- 复用已有基类、JPA 审计或 MyBatis 自动填充及逻辑删除配置，核对实体映射与实际表字段一致，避免重复声明和重复填充。
- 修改存量表时核对六字段现状；缺失项记录差异和本次是否涉及补齐，不在无关改动中自动迁移历史表。需要补齐时说明存量数据回填、兼容与迁移影响。
- 方案评审逐字段核对定义及依据，检查 DDL 与实体映射、填充机制和逻辑删除语义是否一致；缺项或无依据的定义须给出具体修正，不能只检查字段数量。

## SQL 与数据访问

- 默认优先单表查询，条件尽量使用已有索引字段。检查联合索引顺序、选择性、排序和范围条件；避免索引列上的函数、隐式转换和前导通配符等可能妨碍索引利用的写法。
- 业务解析、格式转换、复杂条件分支及可复用计算逻辑优先放在职责明确的代码/已有业务方法中，SQL保持清晰的数据操作边界。保留数据库必要的过滤、排序、分页、合理聚合、约束和原子条件更新/计数，不能为了“代码计算”拉取全表、制造N+1或把原子更新拆成有竞争的先查后写。移出SQL时保持空值、精度、舍入、时区和排序语义，并按实际规模验证成本；不是禁止所有SQL表达式。
- 普通列表/详情/统计查询默认不加行锁，不因“保险”附加FOR UPDATE、FOR SHARE或ORM悲观锁。确有资格竞争、库存/队列领取等一致性需求时，先评估已有原子条件写入、约束和版本机制是否足够；必要锁明确竞争窗口、持有范围、事务和等待预算。删除存量锁前核对调用者和真实保护语义，不能把取消锁等同于解决死锁/性能问题，不能为了无锁另造通用协调框架。
- 新增或改造 UPDATE/DELETE 仅采用单表写入，不生成 JOIN UPDATE、JOIN DELETE 或一条语句修改多表。需要跨表资格、依赖或顺序校验时，先判断原子条件SQL、约束或已有并发机制是否足够；确需多步一致性时在最小事务内完成资格复核、并发保护及条件更新，核对受影响行数；不能简单拆开查询与更新而引入竞争，不能因改成单表宣称不会死锁或丢失原业务规则。按实际路径选择必要的锁与统一锁顺序，不为所有查询自动加锁。
- 批量查询、更新和清理应明确实际扫描/影响行数、索引、执行预算及事务边界。参数个数或每批ID上限不等于扫描量有界，readOnly不代表有超时或事务必短；检查调用者外层事务。批次间等待、远程调用和重试退避放在事务外，失败按项目机制回滚并做有界重试。慢查询是否导致事务持续、锁等待是否是根因以实际证据区分，不凭耗时臆断漏提交；GROUP BY改DISTINCT需保持语义且单独验证执行计划，不能声称改写必然提速。
- 有索引字段不代表实际使用索引。设计列出查询模式、已有索引及预期访问路径；实现与评审在可用环境检查 EXPLAIN。记录真实计划和数据规模，环境不可用时明确待验证，不能宣称已命中索引。
- 不为满足单表偏好拆成 N+1。优先批量查询和内存关联，限制单批大小与内存占用；确需 JOIN 时说明理由、规模和执行计划。
- IN 查询分批，默认每批不超过 500 个参数；项目或数据库限制更严格时遵循更严格值。复用已有批量能力，避免每个调用点各写一套工具。
- 定时任务全量遍历必须分批分页，优先主键或合适索引的游标分页。明确稳定排序、唯一游标、批次大小、扫描边界、失败恢复与幂等，避免深 OFFSET 和一次性加载全表。
- 无适用索引时说明扫描成本及优化选项，根据实际负载决定索引变更；优化器对小表选择扫描可解释记录，不强制使用索引。新增索引考虑写入成本、空间和上线影响。
- 原生 SQL 使用清晰别名，依据实际数据库版本检查保留字；不把普通字段名一概视为所有数据库的保留字。

## 各阶段执行与证据

- 设计：列出实际复用的方法、框架和工具；提供类型签名、方法职责以及查询/索引/批处理方案。
- 方案评审：核对以上决策及例外是否有依据，避免重复实现和无根据的依赖、索引或抽象。
- 实现：按规范编码并运行项目适用的编译、静态检查和相关测试。
- 代码评审：沿真实调用路径检查类型边界、职责、复用、N+1、分页和索引证据；按实际影响定级，证据不足单列待验证项。

## 行为验收案例

1. Java 业务代码反复使用全限定名、固定字段使用 Map 入出参：改用 import 与明确类型；同名冲突和动态协议说明例外。
2. 已有 Repository/Mapper 或业务方法满足需求：引用真实入口复用；不生成等价封装。内部批量结果 Map 不误报为接口 Map。
3. 单表 WHERE 有索引字段但 EXPLAIN 未取得：报告待验证；不声称索引检查通过。
4. 定时任务遍历大表：使用有界批次和稳定游标；循环逐条查库、一次加载全表和深 OFFSET 均需处理。
5. 项目无 Lombok、外部页码从 1 开始：保留已有类型风格与 API 基准，在 JPA 边界转换并验证第一页。
6. 非 Java 变更：跳过此规范，不新增 Java 依赖或验证要求。

7. 新建业务表：六个基础字段全部进入字段清单与 DDL，定义取自真实项目约定；已有公共实体则复用映射。项目约定不明时保留待确认项，不杜撰默认值。
8. 修改存量表且缺少基础字段：报告差异与迁移范围，不擅自修改无关历史表；评审逐项核对字段语义、填充和逻辑删除配置。

9. 字段默认值评审：合理初始状态按项目约定设置；无合理默认值的必填字段显式校验，未知时间不填虚假时间。即使存在 DEFAULT/NOT NULL，也独立检查执行计划，不宣称因此必然走索引。

10. 单语句 if/else、普通和增强 for：return/throw/continue 和调用均放在花括号块内；else if 链保持可读。
11. 复杂条件阈值：两项允许内联；恰好三项及以上提取为具业务含义的谓词，括号分组不规避阈值；已提取谓词无需反复展开。
12. 条件包含空值保护、混合 &&/|| 或有副作用的调用：提取前后短路顺序、异常和调用次数一致，不把条件提前求值为方法实参。

13. 单语句try/catch/finally和方法体：展开为多行块，保留原异常原因及执行语义；空块不补虚假语句，JSON/数组字面量不按控制流块机械改写。

14. 业务状态校验失败：复用项目已有业务异常与准确错误码，避免通用JDK异常；既有业务异常可直接传播，不重复包装。
15. 底层故障：核对cause、重试/回滚和边界映射；不把数据库故障变成不可重试的用户业务错误，不为每个场景新增异常类。

16. 普通列表/单条原子更新：不额外套业务事务，不把readOnly当无事务；框架必要写入事务沿用。多步必须同成同败的操作保留最小有效事务并核对真实回滚。

## Java 契约与仓储边界补充

以下是已确认偏好，应用于本次 Java/SQL 设计、实现和评审；目标项目的真实框架、已有协议与当前授权范围优先。

- 固定字段的方法入参与返回值使用明确对象、DTO、VO、record 或已有模型，不以 Map/JsonNode 隐藏契约。Map 可用于必要的内部索引、查找及动态协议，JsonNode 限于必要的解析/转换边界；确需兼容 Map 输出时由明确对象提供 toMap()，核对字段名、类型、NULL/缺失、顺序及序列化。不能用空 DTO 包一层 Map 规避检查，也不能让动态解析扩散到业务 API。
- Controller 对外 HTTP 标量入参/返回值、参与绑定/序列化的请求与响应字段（含嵌套对象和 record 组件）使用包装类型。迁移验证缺失、默认值、NULL、必填校验、拆箱、Boolean 判断及数值比较；内部辅助方法、Service/Repository、局部计算可继续使用基本类型，保留框架重写签名、byte[] 等二进制协议与 void 无内容响应。
- 每个方法有一个清晰业务目的，流程编排可调用多个步骤；解析、校验、数据访问与远程副作用边界明确。命名遵循所在模块，准确表达对象、动作、单位和状态，布尔谓词语义清楚；不按行数机械拆分、不造转发层，不为改名破坏公开 API、JSON/消息字段或框架契约。
- 业务 SQL 集中在项目已有 Repository/Mapper 数据访问层定义；Service、Controller、Worker、定时任务通过仓储方法调用，不内嵌或拼接执行 SQL，也不新增等价通用 SQL 执行层。Spring Data JPA 项目沿用真实基础 Repository、@Query、必要的 @Modifying 与参数绑定；MyBatis 项目沿用 Mapper，不强行迁移。已有 MysqlBaseRepository 的项目由仓储接口 extends 对应 Po/主键类型的基础接口，不 implements、不再包一层自建基类。Repository 管理 SQL/数据访问，业务映射、循环分页、批次、重试与事务编排由 Service 承担，不把业务塞进接口 default 方法。固定字段映射优先已有类型，避免以运行时表结构探测替代明确契约。
- 新增/改造 UPDATE、DELETE 仅写单表，禁止 JOIN UPDATE、JOIN DELETE 或一条语句修改多表；跨表业务操作分别通过仓储执行，并保留必要的资格复核、条件更新、受影响行数及最小原子边界。查询仍优先单表；必要 JOIN 先核对数据量、索引、过滤及扫描/结果规模，通常不超过 3 张表、最多 5 张（自连接引用计入复杂度），大数据量优先有界批量关联。表少不代表高效，不能捏造规模阈值或执行计划，也不能拆成 N+1/无界加载。
- 非必要不加锁，先检查原子条件更新、唯一约束、幂等与版本；确需跨实例协调时优先评估项目已有分布式互斥是否适合，少用显式数据库行锁。分布式锁不能替代数据库约束或事务原子性，须验证所有写入口、持有者、租约过期、异常释放与失败恢复，不为偏好新增锁框架或承诺绝无死锁。

## 事务入口与字段设计补充

- 必要业务事务声明在具体方法，避免类级注解扩大范围；单数据源沿用已有事务管理器、连接池和 Hibernate/Repository 能力，不自行新增一套管理器。文件解析、校验、转换、远程调用和重试等待在事务外；写入前复核可能变化的状态/版本/租约。允许独立成功的对象或有界批次分别提交，不用外层长事务包整个循环；必须同成同败的业务仍保持最小原子单元。
- Spring 默认代理模式下，必要事务通过实际代理入口调用；同类 method()/this.method() 不会触发被调方法新注解，但已有外层事务仍有效。变量写成 service.method() 也不证明拿到代理，须检查真实 Bean/注入和测试装配；不为了形式新增自注入、AopContext 或无依据 REQUIRES_NEW。与外层同事务的辅助方法不标误导注解，核对传播、checked 异常回滚及实际提交/回滚。
- 建表全部字段及 ALTER 新增/修改字段都应有准确 COMMENT，说明含义、单位或状态；实体注释不等于数据库注释。存在合理初始值时优先 NOT NULL + DEFAULT，尽量避免 NULL；TEXT 按业务保留必要可空性，不强套默认值。未知时间/标识不填假值，不擅改无关历史字段；迁移核对回填、旧写入及序列化语义。六个基础字段继续沿用项目已有约定，默认值与索引利用仍分别验证。
