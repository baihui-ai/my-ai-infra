# 功能生效与恢复开关

适用于前后端、任务、接口等功能的设计、实现、评审与验收。

- 默认交付上线即按需求生效的完整链路。没有明确业务需求或可执行的快速恢复依据时，不主动新增 feature flag、enabled 配置、环境变量、隐藏入口或永远关闭的分支；不把“以后可能灰度”当作新增开关的理由。
- 快速恢复开关必须能在故障处置时有效切换。源码常量、构建时变量或必须重新构建/发布才能更改的配置不满足此条件；需重启的配置也不能默认视为快速恢复，须有满足项目恢复时限的真实操作依据。不要为了获准加开关而自行建设远程配置系统。
- 确需恢复开关时，优先复用项目已有远程配置/控制能力，明确控制位置、责任人、变更权限、生效延迟与缓存/故障语义，以及切换后请求、任务和数据的一致性。只关入口或界面不代表已停止后台副作用。无法证明可操作时，报告恢复缺口，采用已有发布回滚方案或回到直接生效的实现。
- 用户明确要求灰度、租户授权或分阶段开放时按该需求实现；这些业务控制与故障恢复分别说明。保留项目已有开关契约，不在无关变更中批量删除或强制开启历史开关。
- 对本次新增或变更的开关，设计和评审必须说明必要性、生产实际值及来源、缺省值、覆盖优先级和启用交付步骤。默认值与示例须符合当前交付目标，禁止无需求地默认关闭并把手动开启遗漏留给上线人员。
- 验证从实际部署配置或最接近的可用配置出发，沿前端、接口、服务、任务等适用调用链确认功能可达且产生预期业务结果；不能只在测试里强制设为 true 后宣称上线生效。允许的恢复开关还须验证切换、回退和失联行为。无生产环境时明确未验证的实际值和操作证据，不宣称线上已生效。
- 评审发现“发布成功但实际配置使需求功能不可达”，按实际用户影响报告交付缺陷，修正配置、调用链或无依据的开关；不通过补一句“上线记得开启”关闭问题。
